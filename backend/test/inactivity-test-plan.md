# Rencana QA integrasi inactivity

Status: integrasi server dan service sedang dikembangkan bersamaan. Runner menguji sebagian alur HTTP dan menjalankan worker langsung dengan `sendAlert` palsu. Kasus yang belum diuji tetap tercantum di bawah; runner tidak mengklaim cakupan lengkap.

## Menjalankan

Di root repository: `node backend/test/inactivity-api.test.mjs`. Diperlukan Docker, image lokal `postgres:16-alpine` dan `redis:7-alpine`, serta dependency backend terpasang. Runner tidak menarik image. Runner membuat container acak loopback-only dengan tmpfs dan Redis tanpa persistence, database/kredensial acak, serta server lokal dengan environment allowlist dan `DOTENV_CONFIG_PATH` menuju file yang tidak ada di direktori sementara. Token Telegram kosong; guard proses server membatasi listener ke loopback, memblokir TCP keluar selain ke port container sintetis, lookup DNS selain alamat loopback, dan pembuatan subprocess. Guard ini adalah lapisan pengaman tes untuk jalur Node yang digunakan saat ini, bukan sandbox OS yang menjamin isolasi semua native addon/protokol. Jangan menambah jalur jaringan baru tanpa isolasi yang sesuai.

Runner tidak menerima URL database, Redis, server, maupun token dari environment. Cleanup hanya menarget container yang berhasil dibuat oleh run ini. Jangan mengarahkan tes ke service atau data eksternal. `node --test` hanya melewati runner; jalankan secara langsung.

## Kontrak yang perlu dipublikasikan

- Skema saat ini menggunakan `users.inactivity_enrolled_at`, `users.last_transaction_activity_at` dan `inactivity_cases`; migrasi dipanggil saat startup server. `INACTIVITY_AUTO_ENABLED=true` mengikutsertakan registrasi baru. Tegaskan kebijakan akun lama, registrasi web, link akun lama dan repeat contact, termasuk apakah ada backfill.
- Definisi transaksi yang mereset activity: create melalui web/Telegram, update/delete, transaksi invalid, gagal commit, serta atomisitas commit transaksi dan perubahan activity. Tetapkan perilaku admin.
- `POST /telegram/inactivity/response` dengan body `{telegram_user_id, action: 'keep'|'delete', token}`: autentikasi internal, respons/status untuk setiap kegagalan, dan sumber identitas private chat yang tepercaya. Body tersebut tidak membawa chat ID; bot harus memvalidasi private chat sebelum forward, atau kontrak perlu menyertakan bukti konteks yang diverifikasi server. Identitas yang sekadar disediakan caller tidak cukup tanpa autentikasi caller.
- Service saat ini menyediakan `runOnce` dan `sendAlert` injectable; runner menyuntik fake secara langsung dan membuat status `notified` sintetis untuk HTTP. Integrasi server belum menyediakan fake sender injectable; jangan mengandalkan token Telegram nyata atau interval worker dunia nyata.
- `POST /telegram/inactivity/poll-begin`, `/telegram/inactivity/poll-complete`, `/telegram/inactivity/poll-unsafe`, dan `/telegram/inactivity/poll-drained` memerlukan token bot. `poll-begin` memakai `ownerId` dan `requestId` stabil saat retry; hasil penyelesaian poll juga idempoten. Owner lain tidak dapat mengambil alih lease aktif; jika mengambil alih setelah lease habis sementara poll lama belum selesai, `recovery_required` harus mempertahankan fail-closed walaupun owner baru sudah drained. Purge no-response memerlukan owner lease yang valid dan poll yang dimulai setelah `purge_after`, sudah dikonfirmasi drained, tidak ada poll aktif, recovery tidak diperlukan dan heartbeat masih segar (implementasi saat ini dua menit). Tidak ada heartbeat yang memenuhi syarat adalah penundaan yang diharapkan, bukan kegagalan purge. Konfirmasi HTTP saat ini dapat langsung menjalankan `purgeEligible`; prosedur recovery aman masih perlu ditetapkan.
- Jam injectable atau kontrol waktu yang dapat diandalkan: batas eligibility, waktu kirim sukses, deadline 48 jam dan perilaku tepat pada batas; retry dan kegagalan kirim tidak boleh memulai hitung mundur penghapusan.
- Semantik token sekali pakai, expiry, replay, pengguna lain, pending yang sudah digantikan, dan hasil idempoten. Tentukan status respons dan invariants saat respons/worker/activity bersamaan.
- Kontrak penghapusan: hard delete vs anonimisasi, daftar lengkap tabel/kolom yang mengandung data dan PII, retention/legal exceptions, identitas yang boleh tersisa, Redis/cache, serta atomic rollback dan apa yang dianggap selesai.

## Skenario setelah kontrak tersedia

1. Migrasi terhadap akun lama yang dibuat sebelum startup; daftar baru web dan Telegram, hubungkan ulang dan link akun lama. Tegaskan status enrolment dan waktu awal tanpa reset diam-diam.
2. Transaksi valid melalui setiap jalur yang disepakati memperbarui activity; invalid, tidak terautentikasi, akun tidak berhak, dan kegagalan database tidak memperbarui activity atau meninggalkan commit parsial.
3. Admin lama dan baru tidak eligible, tidak dikirimi, dan tidak terhapus meski waktu telah berlalu; perubahan role tepat sebelum worker dieksekusi juga dilindungi.
4. Caller tanpa secret, chat non-private, pemilik lain, token salah/kosong/kedaluwarsa, action invalid dan replay ditolak tanpa mengubah akun, data, status atau deadline. Verifikasi private chat pada boundary bot bila server tidak menerima konteks chat.
5. Kegagalan atau tidak adanya pengiriman notifikasi tidak menandai notifikasi sukses dan tidak memulai atau menyelesaikan penghapusan bahkan setelah lebih dari 48 jam; retry sukses memulai tenggat dari waktu sukses.
6. `keep` oleh pemilik dengan token sah mengaktifkan/reset activity dan membatalkan pending/deadline sesuai kontrak; replay atau worker lama tidak menghapusnya. Baseline HTTP sudah dicakup; race worker masih terbuka.
7. `delete` sah menghapus/anonimkan data dan PII sesuai inventaris serta invalidasi sesi/cache; periksa seluruh tabel terkait dan identitas sintetis, bukan hanya flag `is_deleted`. Akun lain tetap utuh.
8. Tanpa jawaban, sebelum batas 48 jam data tetap ada. Setelah batas, tanpa heartbeat valid, dengan heartbeat yang dimulai sebelum deadline, kedaluwarsa, atau poll belum drained, penghapusan harus ditunda. Setelah heartbeat sah yang dimulai setelah deadline dan dikonfirmasi drained, hapus secara idempoten. Uji callback tertunda diproses sebelum drained sehingga `keep` mencegah purge. Runner mencakup kasus dasar tersebut; batas tepat dan race konfirmasi/poll masih perlu pengujian deterministik.
9. Race deterministik menggunakan barrier/kunci database: dua callback, keep vs delete, keep vs worker, transaksi vs worker, dua worker dan perubahan admin vs worker. Tepat satu hasil legal; tidak ada penghapusan setelah keep/aktivitas yang menang, tidak ada PII parsial, token hanya sekali pakai. Runner menguji keep vs delete secara bersamaan tanpa barrier; run sebelumnya menghasilkan deadlock PostgreSQL `40P01`, sedangkan run setelah perubahan service lulus. Ini belum membuktikan semua interleaving aman.
10. Fault injection pada tahap-tahap penghapusan dan commit memastikan rollback/konsistensi, termasuk retry setelah kegagalan pengiriman atau database.

Tambahkan assertion untuk kasus terbuka setelah kontraknya disepakati. Validasi private chat berada di boundary bot: endpoint saat ini hanya menerima ID user dan tidak dapat membuktikan asal chat dari body tersebut.
